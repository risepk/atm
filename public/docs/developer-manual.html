Architecture

1. Core PHP Architecture & MVC Design

ATM Ledger is constructed with vanilla, framework-less Core PHP 8.2 and MariaDB 10.4. It avoids heavy framework overhead while maintaining strict Model-View-Controller (MVC) separation of concerns.

HTTP Request → .htaccess → public/index.php → Router → Middleware (auth, csrf, role) → Controller → Service → Model (PDO) → View (PHTML)
Database

2. Database Schema & Financial Integrity

Financial accuracy requires immutable design invariants:

  • Primary Keys: BIGINT UNSIGNED AUTO_INCREMENT for permanent sequential identity.
  • UUIDs: CHAR(36) for cross-system and API reconciliation.
  • Monetary Columns: Strictly DECIMAL(18,2). No FLOAT or DOUBLE types exist anywhere in the schema.
  • Virtual Balance Derivation: Portfolio balances are computed dynamically from starting balance + sum of active credits - sum of active debits. Voided transactions are strictly filtered by status != 'voided' AND deleted_at IS NULL.
Financial Math

3. BCMath Financial Calculation Engine

Binary floating point numbers in computing (IEEE 754) produce rounding artifacts (e.g. 0.1 + 0.2 = 0.30000000000000004). In financial ledgers, this drift is completely unacceptable.

Rule: Floating point casting ((float) or floatval()) is strictly banned on financial balances. All addition, subtraction, and comparisons must use CurrencyHelper (which wraps bcadd, bcsub, bccomp with scale 2). 
// Correct Financial Calculation:
$newBalance = CurrencyHelper::sub($currentBalance, $debitAmount);

// Comparison:
if (CurrencyHelper::comp($amount, '0.00') > 0) { ... }
Narration

4. Narration Template Engine & Rapid Entry Integration

The Narration Engine provides dynamic token substitution, generator assistance, and authoritative historical ledger snapshots.

// Narration Architecture: Rapid Entry Hooks into Existing Engine
Rapid Entry (/transactions/rapid)
    ↓
Quick Narration Selection (Active DB Templates)
    ↓
Existing Template Engine (NarrationService / NarrationEngine)
    ↓
Dynamic Required Inputs (Only fields matching pattern tokens)
    ↓
Generated Narration (Live token compilation)
    ↓
Final Narration (Authoritative & freely editable by user)
    ↓
Save Transaction (POST /api/transactions/save with template snapshot)
Architectural Invariant: Zero Logic Duplication

Rapid Entry must not duplicate narration compilation, validation, generator rules, or snapshot storage. It reuses the exact same NarrationEngine.compile(), GeneratorService rules, and TransactionService::createTransaction() payload schema (template_id, template_version, template_payload). Historical transactions remain immutable if templates are updated later.

  • Token Detection: Patterns use bracketed notation: {field_key}. In template creation/editing, the parser auto-infers field types: {stan} → stan, {sender_bank} → bank, {account} → account.
  • Version Preservation: When an admin updates a template, the template version increments. Existing transactions retain their historical narration string and original template_version snapshot.
  • Generator Rules: GeneratorService::generate() creates random 6-digit STANs, bank reference numbers (prefix + YYMMDD + 8 digits), and unique alphanumeric IDs with collision protection.
UI / Frontend

5. Select2 Integration & Tailwind Styling

Searchable comboboxes are powered by Select2 4.1, customized via select2-tailwind.css:

  • Matches Tailwind's rounded-lg, border-gray-300, and ring-indigo-500 focus states.
  • dropdownParent is automatically bound to the closest modal container so typing in search inputs works inside Tailwind modals.
  • select2.min.js and jquery.min.js are loaded in header.php to prevent asynchronous execution race conditions.
Security

6. Security & IDOR Protection

IDOR Isolation: All account and transaction queries verify WHERE user_id = :session_user_id unless the authenticated user holds the admin role.

CSRF Token: All state-changing HTTP POST requests require a valid _csrf_token verified by CSRF::validateToken().

Password Security: Passwords are hashed with bcrypt (PASSWORD_DEFAULT) and input is preserved verbatim without trimming spaces.

XSS Prevention: All user strings displayed in views are sanitized via e() (htmlspecialchars(..., ENT_QUOTES, 'UTF-8')).

Auditing

7. Audit Trail & Mutations

Every sensitive mutation (account creation, bank addition, status toggle, transaction editing, transaction voiding) writes an immutable record to audit_logs with:

user_id • action • entity_type • entity_id • old_values (JSON) • new_values (JSON) • ip_address • created_at

Future Bank Statement Implementation Guide:

When adding future bank layouts (Meezan Bank, UBL, Bank Alfalah, MCB):

  1. Study authentic client sample layout and map visual columns.
  2. Create a new dedicated renderer class implementing StatementRendererInterface.
  3. Never recalculate balances independently; always consume pre-calculated figures from $statementData.
  4. Register the class in StatementRendererFactory and activate the format in statement_formats table.
  5. Add regression tests in tests/run_tests.php proving 100% financial parity with Standard format.
